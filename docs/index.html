Theme Park Dispatch Controller

A FreeRTOS-based ESP32-S3 application that models a theme park emergency-stop and ride-dispatch response path. The project compares a binary semaphore with a direct task notification, measures ISR-to-task latency, and evaluates the design under controlled processor load.

Project Overview

This project is tailored toward embedded software, ride and show control, and safety-critical real-time systems roles. It demonstrates how a time-critical interrupt can be kept short while deferring application work to high-priority FreeRTOS tasks. The design also shows how periodic background tasks affect interrupt response latency.

System Architecture

The button on GPIO18 triggers the ISR. The ISR records a timestamp, applies debounce logic, pulses GPIO19 for external measurement, and signals both bottom-half tasks. The periodic load tasks run on Core 1 and create controlled contention for the response path.

Task Table and WCET Evidence

The periodic task priorities follow a rate-monotonic ladder. Dispatch Lock is the highest-priority safety task, while logging has the lowest priority because it is not safety critical.

Task Role Period Measured WCET WCET + 30% Priority Core
Dispatch Lock Ride dispatch safety interlock 10 ms 362 μs 470 μs 15 Core 1
Motor Control Drive-tire and motion-control workload 20 ms 2255 μs 2931 μs 10 Core 1
Operator Input Operator-panel input processing 50 ms 3358 μs 4366 μs 5 Core 1
Logging Ride event and diagnostic logging 100 ms 3993 μs 5191 μs 2 Core 1

Utilization

U = 470/10000 + 2931/20000 + 4366/50000 + 5191/100000
U = 0.0470 + 0.1466 + 0.0873 + 0.0519
U = 0.3328 = 33.28%

The four-task Rate Monotonic sufficient bound is approximately 75.68%. Since 33.28% < 75.68%, the periodic task set is schedulable under the sufficient RMS test.

Latency Results

Run Mode Direct Notification Maximum Binary Semaphore Maximum
Idle 30 μs 2410 μs
Under Load 2682 μs 2520 μs

The loaded notification path increased by 2682 − 30 = 2652 μs, or approximately 89.4×. The semaphore path increased by 2520 − 2410 = 110 μs, or approximately 1.05×.

Task A runs at priority 15, while both bottom-half tasks run at priority 12. Therefore, Task A can delay the bottom-half response. Tasks B, C, and D run at lower priorities and cannot preempt the bottom-half tasks.

Fault Injection

The induced failure removed portYIELD_FROM_ISR(higher_woken). The program continued to function, but the awakened tasks were no longer guaranteed to run immediately when the ISR exited.

Expected Effect

The bottom-half task would wait until the scheduler naturally selected it, increasing ISR-to-task response time.

Observed Effect

Both handlers still executed, but latency became less predictable and more inconsistent. This demonstrated degraded real-time responsiveness rather than a complete functional failure.

Final Reflection

What I Would Do Differently

If I completed this project again, I would spend more time designing the full architecture before writing code. I initially focused on getting each feature working and then integrated the pieces afterward. Although this approach worked, it created additional debugging because changes to task priorities, workload, or synchronization could affect the entire timing behavior. A more detailed design document containing the task model, priorities, data flow, timing budget, and test plan would make the implementation process more organized.

I would also automate more of the data collection. The project required at least fifty button presses in idle mode and another fifty under load. Automating the collection and export of latency samples would make it easier to calculate the maximum, average, standard deviation, and percentile values. I would also add a dedicated safety-state task and separate the comparison code from the final production path so only one synchronization mechanism is used in the deployed design.

What Was Harder Than Expected

The hardest part was understanding why timing behavior changed under different task loads. The source code could appear correct while the measured response changed significantly because of priorities, preemption, and scheduler timing. Small implementation details such as the placement of timestamps and the use of portYIELD_FROM_ISR() had a visible effect on the results.

It was also more difficult than expected to compare the binary semaphore and direct notification paths fairly. Both handlers respond to the same interrupt, so their order of execution and equal priorities can affect the observed latency. The logic analyzer helped confirm when the ISR entered and exited, while the software timestamps measured when each task began running. Using both methods gave me more confidence that the behavior I observed was real.

Most Valuable Thing Learned

The most valuable lesson was that a real-time system is not considered correct simply because it eventually produces the correct output. It must produce that output within a required deadline. This project showed me why engineers keep ISRs short, defer work to tasks, measure worst-case execution time, assign priorities based on criticality, and verify CPU utilization.

I also learned the importance of validating assumptions with measured evidence. Theoretical scheduling analysis showed that the periodic task set was schedulable, but the latency measurements showed how a higher-priority task could still delay the emergency-response path. This combination of theory, software instrumentation, and logic-analyzer evidence is directly applicable to embedded control and ride-and-show engineering roles.
